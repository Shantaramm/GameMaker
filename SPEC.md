# SPEC: Генератор сюжетных RPG по брифу (MVP)

> Документ для Claude Code. Работай по этапам из раздела 12 строго по порядку: каждый этап заканчивается проверкой из «Критериев приёмки». Не переходи к следующему этапу, пока текущий не проходит. Если в спецификации что-то противоречит реальному API GigaChat — сверься с официальной документацией (ссылки в разделе 14), исправь и отметь это в `NOTES.md`.

## 1. Цель

Веб-сайт, где пользователь:
1. Пишет идею игры (одна фраза или подробный текст).
2. По желанию нажимает «Развернуть в бриф», и ИИ превращает идею в подробный сценарный бриф, который пользователь правит.
3. Нажимает «Создать игру». Бэкенд через GigaChat генерирует игру **как данные** (JSON по строгой схеме), собранные из примитивов движка, и проверяет её. Графика не генерируется нейросетью: GigaChat только описывает внешность персонажей и сцен через параметры пиксельного движка, а рисует движок кодом (раздел 5.7).
4. Играет в браузере: сцены, диалоги с выборами, пошаговые бои, инвентарь, концовки.
5. Получает ссылку на игру, по которой может сыграть кто угодно.

Главный принцип: **LLM не пишет код.** LLM заполняет структуру из примитивов, а движок (код, который пишем мы) её исполняет. Всё, что можно посчитать кодом (баланс боя, проверка проходимости), считается кодом, а не моделью.

## 2. Рамки MVP

**Входит:**
- один жанр: коридорная сюжетная RPG на 15–30 минут, 5–8 сцен, 1–3 концовки;
- герой и максимум один компаньон (компаньон в бою не участвует, только в диалогах);
- пошаговый бой: 1–3 врага, действия «Атака / Навык / Предмет / Побег»;
- пиксельные портреты персонажей и врагов (с эмоциями) и пиксельные фоны сцен, которые рисует движок кодом из параметров (раздел 5.7);
- сохранение прогресса в `localStorage`;
- шеринг по ссылке `/play/{game_id}`.

**Не входит (не делать):** аккаунты и авторизация, оплата, лента игр, сетевая игра, редактор игры, анимации спрайтов, звук, произвольные скрипты в песочнице, перегенерация отдельных блоков.

## 3. Стек

- **Бэкенд:** Python 3.11+, FastAPI, Pydantic v2, httpx (async), SQLite (через `sqlite3` или SQLModel), uvicorn.
- **Фронтенд:** Vite + TypeScript, без фреймворка или с Preact (на выбор, но лёгкий). Рендер — DOM + CSS, без игровых движков.
- **LLM:** GigaChat API (REST, напрямую через httpx; официальный SDK `gigachat` допустим, если упрощает). Только текст и JSON, генерация изображений GigaChat не используется.
- **Графика:** собственный пиксельный движок на TypeScript + Canvas 2D (раздел 5.7). Библиотека деталей — JSON-файлы в `/pixelart/library`, общие для фронта (рендер) и бэкенда (валидация, каталог для промптов).
- **Общая схема игры:** источник истины — Pydantic-модели на бэкенде. Из них генерируется JSON Schema (`schema/game.schema.json`) и TypeScript-типы для фронта (через `json-schema-to-typescript` или вручную, но синхронно).

## 5. Движок: примитивы

Игра — это документ `Game`. Все ссылки между объектами — по строковым `id` (латиница, `snake_case`). Ниже — модели (переведи в Pydantic с `extra="forbid"`).

### 5.1 Верхний уровень

```
Game {
  schema_version: "1"
  meta: { title, logline, tone, art_style, language: "ru", est_minutes }
  hero: Character            # главный герой (role = "hero")
  characters: Character[]    # остальные NPC, включая компаньона
  stats_template: { hp, attack, defense, focus }   # стартовые статы героя (заполняет balance.py)
  skills: Skill[]
  items: Item[]
  enemies: Enemy[]
  flags: FlagDef[]           # все флаги сюжета объявлены заранее
  scenes: Scene[]
  start_scene: scene_id
  endings: Ending[]
}
```

### 5.2 Персонажи

```
Character {
  id, name, role: "hero" | "companion" | "npc" | "antagonist",
  description,          # 2–4 предложения: внешность, характер, мотивация
  appearance: PortraitSpec   # параметры пиксельного портрета (5.7.2)
}
```

Правило: `appearance` задаётся **один раз** при генерации и больше не меняется. Портрет детерминирован: одинаковые параметры дают одинаковую картинку, поэтому персонаж выглядит одинаково во всей игре автоматически.

### 5.3 Бой

```
Skill { id, name, description, cost_focus: int, effect: Effect[], target: "enemy" | "self" }
Item  { id, name, description, consumable: bool, effect: Effect[] }
Enemy { id, name, description, tier: 1..5,
        appearance: PortraitSpec | CreatureSpec,   # люди-враги — портрет, монстры — существо (5.7.3)
        hp?, attack?, defense?,        # НЕ заполняет LLM — заполняет balance.py по tier
        abilities: EnemyAbility[] }    # 0–2 особых действия
EnemyAbility { name, effect: Effect[], every_n_turns: int }
```

### 5.4 Сцены и события

```
Scene {
  id, title, background: BackgroundSpec,      # параметры пиксельного фона (5.7.4)
  intro: str,                 # 1–3 абзаца описания
  events: Event[]             # выполняются по порядку
}

Event = один из:
  Dialogue  { type: "dialogue", id, nodes: DialogueNode[], start_node }
  Battle    { type: "battle", id, enemies: enemy_id[], on_win: Effect[], on_lose: "game_over" | Effect[] , can_flee: bool }
  Choice    { type: "choice", id, prompt, options: ChoiceOption[] }    # выбор без собеседника
  Narration { type: "narration", id, text }
  Transition{ type: "goto", to: scene_id | ending_id, condition?: Condition }

DialogueNode {
  id, speaker: character_id | "narrator",
  text,
  emotion?: "neutral" | "angry" | "sad" | "happy" | "scared" | "surprised",   # меняет глаза, брови и рот на портрете
  choices: DialogueChoice[]      # пусто → переход к next
  next?: node_id | "end"
}
DialogueChoice { text, condition?: Condition, effects: Effect[], next: node_id | "end" }
ChoiceOption   { text, condition?: Condition, effects: Effect[] }
Ending { id, title, text, kind: "good" | "neutral" | "bad" }
```

### 5.5 Условия и эффекты (мини-язык без кода)

Структурные объекты, а не строки с выражениями:

```
Condition = { all: Condition[] } | { any: Condition[] } | { not: Condition }
          | { flag: flag_id, is: bool }
          | { has_item: item_id }
          | { stat: "hp"|"attack"|"defense"|"focus", op: ">="|"<=", value: int }

Effect = { set_flag: flag_id, value: bool }
       | { give_item: item_id } | { take_item: item_id }
       | { learn_skill: skill_id }
       | { mod_stat: stat, delta: int }
       | { heal: int } | { damage: int }
       | { goto: scene_id | ending_id }
```

### 5.6 Рантайм (фронтенд)

- `GameState { scene_id, event_index, node_id?, hero_stats, inventory, skills, flags, battle? }`.
- Движок проходит `scene.events` по порядку; `goto` прерывает сцену.
- Если сцена закончилась без `goto` — это ошибка валидатора, в рантайм не должна попасть.
- Варианты с невыполненным `condition` показываются серыми с подсказкой («Нужно: ключ от архива»), а не скрываются.
- Бой: инициатива у героя; урон = `max(1, attack − defense/2) ± 20%`; навык тратит `focus`; побег 50%, если `can_flee`.
- Состояние сохраняется в `localStorage` под ключом `game:{id}` после каждого события.

### 5.7 Пиксельный движок

Принцип тот же, что у игрового движка: **LLM не рисует пиксели, а выбирает и настраивает готовые детали.** Детали рисуются один раз (их создаёт Claude Code на этапе 2а и они вручную проверяются), а движок собирает из них картинку по параметрам.

#### 5.7.1 Формат деталей и палитр

- Деталь — JSON: `{ id, slot, description, w, h, anchor: [x, y], pixels: string[], variants?: {...} }`.
- `pixels` — массив строк одинаковой длины, каждый символ — индекс цвета в **слотах палитры**, а не конкретный цвет:
  `.` — прозрачный, `o` — контур, `s/S` — кожа (свет/тень), `h/H` — волосы, `c/C` — основной цвет одежды, `a/A` — акцентный цвет, `e` — глаза, `w` — белый, `m` — металл.
- Цвета подставляются при рендере из `PortraitSpec`, поэтому одна деталь даёт сотни вариантов.
- Тени и свет детали содержат сами (буквы в верхнем регистре). Движок затемняет их автоматически: `S = s * 0.75` в HSL, если тень не задана явно.
- Палитры (`palettes.json`) — именованные наборы цветов: `skin_tones` (8+), `hair_colors` (12+), `cloth_colors` (16+). LLM выбирает цвета **только по имени** из палитры, чтобы картинка оставалась гармоничной.
- Рендер: Canvas 2D, `imageSmoothingEnabled = false`, CSS `image-rendering: pixelated`, целочисленное масштабирование (×4…×8 по размеру экрана).

#### 5.7.2 Портрет (`PortraitSpec`)

Холст 48×48, портрет по плечи. Слои снизу вверх: `back_hair → outfit → head → face (eyes, brows, mouth) → front_hair → accessory`.

```
PortraitSpec {
  head: part_id,        # форма лица (овал, квадрат, худое, круглое, старое…)
  skin: palette_name,
  hair: part_id | "none", hair_color: palette_name,
  eyes: part_id, eye_color: palette_name,
  brows: part_id,
  mouth: part_id,
  facial_hair?: part_id,
  outfit: part_id, outfit_color: palette_name, accent_color: palette_name,
  accessory?: part_id[],   # до 2: очки, шрам, шляпа, повязка, серьга, капюшон…
  bg_color: palette_name   # фон портрета
}
```

Эмоции: у деталей `eyes`, `brows`, `mouth` есть `variants` для каждой эмоции из 5.4 (`neutral` — обязателен, остальные — если нет, берётся `neutral`). Рантайм рисует портрет с эмоцией из текущего `DialogueNode.emotion`. Готовые портреты кэшируются в памяти по ключу `(character_id, emotion)`.

Минимальная библиотека для MVP: 6 голов, 14 причёсок (включая «лысый» и капюшон), 6 глаз, 5 бровей, 6 ртов, 4 варианта растительности на лице, 12 нарядов (плащ детектива, доспех, мантия мага, деловой костюм, рабочая куртка, платье, броня sci-fi, лохмотья и т. д.), 12 аксессуаров.

#### 5.7.3 Существа (`CreatureSpec`)

Для монстров и не-людей. Холст 64×64.

```
CreatureSpec {
  body: part_id,          # слизень, волк, скелет, призрак, голем, жук, робот, дракончик, культист-тень…
  color: palette_name, accent_color: palette_name,
  features?: part_id[],   # до 3: рога, крылья, третий глаз, шипы, корона, светящиеся глаза…
  size: "small" | "medium" | "large"   # целочисленный масштаб на экране боя
}
```

Минимальная библиотека: 10 тел, 10 особенностей. У каждого тела `anchor`-точки для особенностей (`head_top`, `back`, `face`), чтобы рога и крылья вставали на место.

#### 5.7.4 Фон (`BackgroundSpec`)

Холст 160×90 (16:9), слои снизу вверх:

```
BackgroundSpec {
  setting: "indoor" | "outdoor",
  time: "day" | "dusk" | "night",
  sky?: part_id,              # для outdoor: градиент + звёзды/луна/солнце/облака
  far: part_id,               # силуэты: город, горы, лес, стена комнаты, пещера, корабль…
  props: { id: part_id, x: 0..160 }[],   # до 5 предметов на переднем плане: дверь, стол, фонарь, дерево, полка, ящики…
  ground: part_id,            # пол или земля: брусчатка, паркет, трава, камень, металл
  overlay?: "rain" | "fog" | "snow" | "dust" | "none",   # анимируется в рантайме
  mood_palette: palette_name  # общая цветовая гамма сцены (тонирует все слои)
}
```

Процедурные слои (градиент неба, звёзды, дождь, туман) рисуются кодом с детерминированным `rng(seed)`, где `seed = hash(game_id + scene_id)`. Минимальная библиотека: 6 небес, 10 дальних планов, 25 предметов, 6 типов земли, 8 настроенческих палитр.

#### 5.7.5 Каталог для LLM

Скрипт `scripts/build_catalog.py` читает `/pixelart/library` и пишет `catalog.md`: для каждого слота список `id — короткое описание`, плюс имена палитр. Каталог подставляется в промпты, и LLM выбирает только из него. Валидатор отклоняет несуществующие id и цвета.

#### 5.7.6 Страница PixelLab (для разработки)

`/lab` на фронте: выпадающие списки для каждого слота, превью портрета со всеми эмоциями, существа и фона; кнопка «Случайно». Нужна, чтобы руками проверять библиотеку деталей и видеть, что собрал GigaChat. Не показывается пользователям в навигации.

## 6. Пайплайн генерации

Генерация идёт **по шагам**, а не одним гигантским запросом: так GigaChat держит структуру надёжнее, а ошибки локализуются.

### 6.1 Шаг 0 — бриф (по кнопке «Развернуть»)
Вход: идея пользователя. Выход: markdown-бриф по фиксированному шаблону (герой, предыстория, мир, тон, антагонист, 5–8 ключевых сцен, варианты финала) плюс 2–3 уточняющих вопроса. Это свободный текст, не JSON. Пользователь правит бриф в textarea.

### 6.2 Шаг 1 — каркас
Вход: бриф и `catalog.md`. Выход JSON: `meta`, `hero`, `characters` (вместе с `appearance`), `flags`, список сцен с `id/title/краткое содержание/какие события (типы)/background`, `endings`. Без диалогов. Внешность всех персонажей выбирается здесь, за один запрос, чтобы персонажи были визуально разными (промпт требует разные причёски, цвета одежды и силуэты у главных героев).

### 6.3 Шаг 2 — сцены
Для каждой сцены отдельный запрос: вход — каркас целиком, бриф и `catalog.md`, выход — полный `Scene` с событиями и диалогами (включая `emotion` у реплик). Для боевых событий LLM указывает только врагов (`id`, имя, описание, `tier`, способности, `appearance`) — без чисел.

После шага 2 сборка `skills` и `items` — отдельным запросом по всем упомянутым id (или в шаге 1, если удобнее; задокументируй выбор в NOTES.md).

### 6.4 Шаг 3 — баланс (код, без LLM)
`balance.py` выставляет статы врагов по `tier` и позиции сцены (кривая сложности: ранние сцены легче) и стартовые статы героя. Формулы — константы в одном месте, чтобы их было легко крутить.

### 6.5 Шаг 4 — проверка и автопочинка
`validator.py` → список ошибок с путём (`scenes[3].events[1].nodes[4].next: unknown node 'n9'`). Если есть ошибки — отправить в GigaChat только проблемный фрагмент + список ошибок + схему, попросить исправленный фрагмент. Максимум 3 итерации, затем статус `failed` с понятной ошибкой для пользователя.

### 6.6 Шаг 5 — плейтест
`simulator.py` (раздел 7.2). Если бой невыигрываемый — `balance.py` понижает статы врага и повторяет. Если концовка недостижима — назад в шаг 4 с этой ошибкой.

### 6.7 Графика
Отдельного шага нет: внешность уже выбрана в шагах 1–2 как параметры, рисует фронт при загрузке игры. Бэкенд хранит только JSON. Если валидатор находит неизвестную деталь или цвет — это обычная ошибка для автопочинки (6.5); если починить не удалось, валидатор подставляет ближайшую деталь того же слота (дефолт из библиотеки) и пишет предупреждение, а не валит игру.

### 6.8 Прогресс
Генерация — фоновая задача (`asyncio` task или `BackgroundTasks`). Статусы: `queued → outline → scenes (k/n) → balance → validate → playtest → ready | failed`. Фронт опрашивает `GET /api/games/{id}/status` каждые 2 секунды.

## 7. Проверки

### 7.1 Валидатор (обязателен)
- JSON соответствует схеме (Pydantic).
- Все id уникальны в своём пространстве; все ссылки разрешаются.
- Каждый диалог: `start_node` существует, все `next` существуют, нет узлов-сирот, из каждого узла достижим `end`.
- Каждая сцена заканчивается `goto` (безусловным или набором условных с гарантированным покрытием, в MVP — требуем, чтобы последний `goto` был безусловным).
- Из `start_scene` достижима хотя бы одна концовка; все сцены достижимы.
- Все используемые флаги объявлены в `flags`.
- Все id деталей в `appearance` и `background` существуют в библиотеке и подходят к слоту; все цвета — имена из `palettes.json`; у главных героев (`hero`, `companion`, `antagonist`) не совпадают одновременно причёска, цвет волос и наряд.
- Ограничения размера: 5–8 сцен, ≤ 12 персонажей, ≤ 40 узлов в одном диалоге, длина реплики ≤ 400 символов.

### 7.2 Headless-плейтест (обязателен)
- Бот проходит игру 50 раз со случайными выборами (сид фиксирован для воспроизводимости).
- Метрики: доля прохождений, дошедших до концовки; какие концовки достигнуты; доля побед в каждом бою (бот в бою: атака, навык при наличии фокуса, лечится при HP < 30%).
- Требования: каждый бой выигрывается в ≥ 70% симуляций; хотя бы одна концовка достигается; нет зацикливаний (лимит шагов 2000).
- Отчёт сохраняется вместе с игрой (`playtest_report`) — пригодится для отладки.

## 8. GigaChat-клиент

- Авторизация: `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth`, заголовки `Authorization: Basic {GIGACHAT_AUTH_KEY}`, `RqUID: {uuid4}`, `Content-Type: application/x-www-form-urlencoded`, тело `scope={GIGACHAT_SCOPE}`. Токен живёт 30 минут — кэшировать и обновлять заранее (за 60 секунд до `expires_at`).
- Базовый URL API: `https://api.giga.chat` (старый `gigachat.devices.sberbank.ru` выводится из эксплуатации). Вынести в env.
- Чат: `POST /v1/chat/completions`. Модель — из env. По умолчанию: `GIGACHAT_MODEL_TEXT=GigaChat-2-Max` для сцен и брифа, `GIGACHAT_MODEL_FAST=GigaChat-2` для автопочинки. Перед началом работы вызвать `GET /v1/models` и записать реальный список в NOTES.md.
- Генерацию изображений GigaChat не использовать (в запросах не передавать `function_call`, чтобы модель не вызывала встроенный text2image).
- TLS: эндпоинты Сбера используют сертификат НУЦ Минцифры. Путь к корневому сертификату — env `GIGACHAT_CA_BUNDLE`; передавать в `httpx(verify=...)`. Отключать проверку сертификата нельзя.
- Ретраи: 3 попытки с экспоненциальной задержкой на 429/5xx/таймаут. Таймаут чата 120 с.
- Логировать каждый запрос (шаг, модель, длительность, токены из `usage`) в `data/logs/{game_id}.jsonl`, без ключа и токена.

### 8.1 Надёжное получение JSON
GigaChat может обернуть JSON в ```json или добавить текст. `json_utils.py`:
1. Вырезать первый сбалансированный JSON-объект из ответа.
2. `json.loads`; при ошибке — один запрос на починку («Верни только исправленный валидный JSON»).
3. Затем Pydantic-валидация; её ошибки уходят в автопочинку (6.5).

В промптах всегда: схема фрагмента, один короткий пример, требование «ответ — только JSON, без пояснений».

## 9. Промпты

Лежат в `backend/app/generation/prompts/*.md`, подставляются через простые плейсхолдеры `{{brief}}`, `{{outline}}`, `{{schema}}`. Требования к содержанию:
- **brief.md**: роль — сценарист нарративных RPG; шаблон брифа; запрет на чужие известные вселенные и персонажей (только оригинальное).
- **outline.md**: роль — геймдизайнер и художник по персонажам; лимиты (5–8 сцен, 1–3 концовки, минимум 2 боя, минимум 1 значимый выбор, влияющий на концовку через флаг); внешность и фоны — только из `{{catalog}}`; внешность должна соответствовать `description` (детектив — плащ, старик — седые волосы).
- **scene.md**: стиль реплик — живые, короткие, у каждого персонажа свой голос; у реплик проставлена `emotion`, соответствующая тексту; 1–2 выбора в диалоге должны иметь последствия (флаг, предмет, статы); боевые события — только враги, tier и внешность из `{{catalog}}`.
- **fix.md**: «Вот фрагмент, вот ошибки, вот схема — верни исправленный фрагмент целиком».

## 10. HTTP API бэкенда

```
POST /api/brief            { idea }                  → { brief_markdown, questions[] }
POST /api/games            { brief }                 → { game_id }        # запускает генерацию
GET  /api/games/{id}/status                          → { status, step, progress, error? }
GET  /api/games/{id}                                 → Game (только при ready)
GET  /api/pixelart/library                           → вся библиотека деталей и палитр (кэшируется)
```

Ограничения: длина брифа ≤ 8000 символов; не более 3 одновременных генераций на сервер (очередь); простой rate limit по IP (5 игр в час).

## 11. Фронтенд

1. **Главная.** Заголовок и одна строка о продукте. Большое поле «Опиши свою историю». Кнопки «Развернуть в бриф» и «Создать игру». Под полем 3 кликабельных примера идей.
2. **Бриф.** Textarea с брифом от ИИ, уточняющие вопросы над ним, кнопка «Создать игру».
3. **Генерация.** Шаги со статусами (каркас, сцены k/n, проверка, плейтест). Ориентир по времени. Как только готов каркас — показать пиксельные портреты персонажей («Твои герои»), чтобы ожидание было интереснее.
4. **Игра.** Пиксельный фон сцены на весь экран (с анимированным overlay), сверху вниз: текст сцены → диалоговое окно с пиксельным портретом слева (эмоция меняется по реплике), именем и репликой, кнопками выборов. Шрифт интерфейса — пиксельный с поддержкой кириллицы (например, свободный шрифт с Google Fonts, проверить кириллицу). Бой — отдельный экран: существа и враги, полосы HP, панель действий, лог боя; при ударе — короткая вспышка или тряска спрайта. Инвентарь — выезжающая панель. Экран концовки с кнопкой «Поделиться» (копирует ссылку).
5. Адаптивность: должна нормально работать на телефоне (ширина 375px) — это будущий Telegram Mini App.

## 12. Этапы работы и критерии приёмки

**Этап 1 — схема и движок без ИИ.**

**Этап 2б — рантайм на фронте.**

**Этап 3 — GigaChat-клиент.**
