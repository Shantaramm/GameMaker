# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Состояние проекта

`SPEC.md` — источник истины по требованиям. Работа идёт по этапам из `SPEC.md` §12 строго по порядку. Следующий этап не начинается, пока не выполнен критерий приёмки текущего. Спецификация переписана в версию 2: игра — RPG с видом сбоку (ходьба без прыжков, тап-навигация, локации с этажами, торговцы, экипировка, опыт, квесты, пошаговые бои при касании врага). Порядок этапов: 1 → 2а → 1б → 2в → 2б → 3…6. Готовы 1, 2а, 1б (схема v2, `levels.py`, бот-исследователь, демо-игра v2), 2в (спрайты в полный рост, тайлсеты, иконки) и 2б (играбельная демо-игра на `/play/demo`). Этапы 3–5 (клиент GigaChat, пайплайн, промпты) реализованы и покрыты тестами без сети, но **приёмка ждёт ключа GigaChat**; этап 6 (сайт и весь путь пользователя) работает на демо-провайдере. Когда появится ключ: положить его в `.env`, получить сертификат НУЦ в `certs/`, прогнать `--smoke`, затем приёмку этапов 4–5 и правку промптов по реальным ошибкам (записывать в `NOTES.md`). Отклонения от спецификации, правила, которых в ней нет, реальные id моделей GigaChat и типичные ошибки генерации записываются в `NOTES.md` (§15). Прочитай его перед изменением движка или рантайма.

## Архитектура

**Главный принцип: LLM не пишет код и не рисует пиксели.** GigaChat заполняет документ `Game` (JSON) из примитивов движка и выбирает детали графики по id из каталога. Всё, что можно посчитать, считает код: статы врагов (`balance.py`), проверку ссылок и достижимости (`validator.py`), проходимость (`simulator.py`).

**Схема — единый контракт для трёх частей системы.** Pydantic-модели в `backend/app/engine/schema.py` (`extra="forbid"`) — источник истины. Из них генерируется `schema/game.schema.json`, из неё — TS-типы для фронта. Меняя модель, синхронно обновляй JSON Schema, TS-типы, промпты (`{{schema}}`), валидатор и `tests/fixtures/demo_game.json`.

**Условия и эффекты — структурные объекты, а не строки-выражения** (§5.5). Они исполняются в двух местах: в TS-рантайме (`frontend/src/engine/` — `conditions.ts`, `effects.ts`, `battle.ts`) и в Python-симуляторе (`simulator.py`). Меняя правило в одном месте, меняй и во втором. Семантика должна совпадать, в том числе формула урона `max(1, attack − defense/2) ± 20%` и побег с вероятностью 50%.

**Рантайм** (`frontend/src/pages/Play.ts`): `GameController` (`engine/runtime.ts`) держит состояние и логику взаимодействий и общается с интерфейсом через `GameUI` — каждое окно (диалог, бой, лавка) это промис; `MapScene` (`world/scene.ts`) рисует карту и превращает тапы и клавиши в движение и вызовы `controller.interact`. Отладочный хук `window.__rpg` использует сквозной тест.

**Мир описывается смыслом, геометрию строит код.** LLM задаёт локацию темой, этажами, зонами и объектами в зонах; `backend/app/engine/levels.py` детерминированно собирает из этого `Level` (тайлы, этажи, лестницы, координаты объектов) и сохраняет его внутри игры-JSON. Фронт уровень только рисует, симулятор ходит по тому же `Level` — второй реализации сборщика на TypeScript быть не должно.

**Пайплайн генерации** (`backend/app/generation/pipeline.py`) знает только интерфейс `LLM.complete()` из `backend/app/llm/` (провайдеры `gigachat`, `demo`, `relay` — ответы пишет оператор, `ScriptedLLM` для тестов; выбирает `LLM_PROVIDER`). Шаги возвращают фрагменты из `generation/fragments.py`; ошибка валидатора уходит в починку только того фрагмента, к которому относится её путь (`Pipeline.route`). Промпты — `generation/prompts/*.md`. Пайплайн идёт по шагам, а не одним запросом: бриф (свободный markdown) → каркас (персонажи с внешностью, квесты, список локаций) → по одному запросу на локацию → предметы и магазины → баланс (код) → уровни (код) → валидатор и автопочинка (не более 3 итераций, в LLM отправляется только сломанный фрагмент) → headless-плейтест (бот-исследователь, 50 прогонов с фиксированным сидом). Работает как фоновая задача, статусы опрашиваются через `GET /api/games/{id}/status`. Ответ LLM всегда проходит через `json_utils.py`: вырезать сбалансированный JSON → `json.loads` → один запрос на починку → Pydantic.

**Пиксельный движок** (`frontend/src/pixel/`, Canvas 2D). Детали в `/pixelart/library/*.json` — это строки символов, где символ означает **слот палитры**, а не цвет. Конкретные цвета подставляются при рендере по именам из `palettes.json`. JSON не правят руками: его пишут генераторы `pixelart/tools/*.py`. Библиотека общая для трёх потребителей: фронт по ней рисует (бандлится через `import.meta.glob`), бэкенд по ней валидирует (`backend/app/engine/art.py`, вызывается из `validate()` по умолчанию), `catalog.md` уходит в промпты. Каждая деталь ставится своим `anchor` в общую точку привязки слоя из `layout.json`, поэтому слои не съезжают. Расширения формата (`back`, `clip`, `points`, `attach`, `setting`) и дополнительные символы палитры описаны в `NOTES.md`. Рендер детерминирован: портрет кэшируется по ключу `(character_id, emotion)`, процедурные слои фона используют `seed = hash(game_id + scene_id)`. Если деталь неизвестна и автопочинка не помогла, подставляется дефолт того же слота с предупреждением, игра не падает.

**Инварианты валидатора, на которые опирается рантайм:** все ссылки и флаги объявлены; все локации достижимы по выходам, все объекты — по этажам и лестницам; из каждого узла диалога достижим `end`; из `start_location` достижима хотя бы одна концовка; нет запертых дверей с ключом за ними; каждый бой выигрывается не менее чем в 70% симуляций. Рантайм не обрабатывает нарушения этих правил, потому что они туда не должны попасть.

## Ограничения MVP

В MVP не делать: прыжки и платформинг, бой в реальном времени, случайные встречи, авторизацию, оплату, звук, анимацию спрайтов, редактор игр, генерацию изображений через GigaChat (не передавать `function_call`). Интерфейс на русском, верстка должна работать при ширине 375px (будущий Telegram Mini App). Страница `/lab` (PixelLab) нужна только разработчикам и в навигации не показывается.
